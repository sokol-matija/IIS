01

What This App Does

A full-stack system that demonstrates how enterprise software components communicate — using REST, SOAP, GraphQL, and gRPC, all in one project.

The Elevator Pitch

Imagine a category manager — you can create categories like "Electronics" or "Books," search them, validate their data, and check the weather. Sounds simple, right?

The twist: this one app talks to itself in four completely different languages. It's like a United Nations building where every department speaks a different language, but they all work together seamlessly.

R

REST

The everyday language — simple, direct requests like "give me all categories" or "create this one."

S

SOAP

The formal, bureaucratic language — wraps every message in an XML "envelope" with strict rules.

G

GraphQL

The "pick exactly what you want" language — you specify which fields you need, nothing more.

g

gRPC

The fast, binary language — used for server-to-server calls where speed matters more than readability.

Let's Trace a Real Action

You open the app, log in, and search for a category named "tech." Here's the journey your request takes — from your fingertip to the database and back:

1
You type your email and password

The frontend (React app in your browser) sends your credentials to the backend.

2
The backend checks your identity

It looks up your email in the database, verifies your password, and issues a JWT token.

3
You navigate to SOAP Search

You type "tech" and hit search. The frontend builds a SOAP envelope (XML message) and sends it to the backend.

4
The backend searches using XPath

It reads an XML file, uses XPath to find matching categories, and wraps the results in a SOAP response.

5
Results appear on screen

The frontend parses the SOAP response, extracts the categories, and renders them in a table. Total time: under a second.

Four Languages, One System

Like a multilingual embassy, each protocol serves a different purpose — and knowing when to use which one is what separates good architecture from chaos.

REST: The Everyday Conversation

REST is like texting — short, casual, direct. You send a message, you get a reply. No formalities required.

CODE 
// backend/src/routes/categories.ts
router.get("/", authenticate, async (req, res) => {
  const categories = await prisma.category.findMany();
  res.json({ data: categories });
});
PLAIN ENGLISH

This is the file where category routes live

When someone asks for all categories (GET /), first check they're logged in...

...then go to the database and grab every category

Send them back as JSON data

SOAP: The Formal Letter

SOAP is like sending a formal certified letter. Every message goes inside an envelope with a specific format. More verbose, but enterprise systems (banks, hospitals) love it because it's predictable and self-documenting.

CODE 
// frontend/src/api/soap.ts
const envelope = `<?xml version="1.0"?>
<soap:Envelope
  xmlns:soap="...soap/envelope/"
  xmlns:tns="http://iis.hr/categories">
  <soap:Body>
    <tns:SearchCategoriesRequest>
      <tns:term>${escapeXml(term)}</tns:term>
    </tns:SearchCategoriesRequest>
  </soap:Body>
</soap:Envelope>`;
PLAIN ENGLISH

This is the file where the frontend builds SOAP requests

Start the XML document and open the SOAP envelope — like the outer envelope of a formal letter

Declare which "namespace" (department) we're writing to

Open the body — this is where the actual message goes

Say "I want to search categories" — that's our request type

Include the search term (safely escaped so special characters don't break the XML)

Close everything up — envelope sealed, ready to send

GraphQL: The Custom Order

GraphQL is like a build-your-own-salad bar. Instead of getting a fixed plate, you specify exactly which ingredients (fields) you want. Only need the name and slug? Ask for just those. Need everything? Ask for everything.

CODE 
// backend/src/graphql/schema.ts
const typeDefs = gql`
  type Category {
    id: Int!
    name: String!
    slug: String!
    description: String
  }

  type Query {
    categories: [Category!]!
    category(id: Int!): Category
  }
`;
PLAIN ENGLISH

This file defines what data is available via GraphQL

A Category has these fields — the "!" means "required, never null"

id: a number that identifies this category

name and slug: required text fields

description: optional text (no "!" = can be null)

You can ask for a list of all categories...

...or a single category by its id

gRPC: The Encrypted Radio

Protocol Buffers define the message format in a .proto file. It's like an encrypted military radio — humans can't read the transmissions, but the machines on both ends know exactly what's being said. Blazing fast.

CODE 
// grpc-server/proto/weather.proto
service WeatherService {
  rpc GetTemperature(TemperatureRequest)
    returns (TemperatureResponse);
}

message TemperatureRequest {
  string city = 1;
}

message WeatherStation {
  string city = 1;
  string temperature = 2;
  string description = 3;
}
PLAIN ENGLISH

This is the "contract" between the backend and gRPC server

The WeatherService offers one operation: GetTemperature

You send a city name, you get back weather data

 

The request message: just a city name as text

The "= 1" is a field number (for binary encoding, not a value)

 

The response: each weather station has city, temperature, and description

These field numbers let gRPC encode data in compact binary format

Data Guardians

Before anything enters the database, it must pass through a gauntlet of validators — like customs officers checking every piece of luggage at a border crossing.

The Database: Where Everything Lives

The project uses SQLite through Prisma. Think of the Prisma schema as the blueprint for your filing cabinet — it says "this drawer holds categories, each with a name, slug, and optional description."

CODE 
// backend/prisma/schema.prisma
model Category {
  id          Int       @id @default(autoincrement())
  name        String
  slug        String    @unique
  description String?
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt
}
PLAIN ENGLISH

This file defines the shape of data in the database

A Category is a "table" — a collection of items with these fields:

id: auto-generated number, unique identifier (like a Social Security number)

name: required text (e.g., "Electronics")

slug: required unique text, URL-friendly (e.g., "electronics")

description: optional text (the "?" means it can be empty)

createdAt: automatically set to "right now" when created

updatedAt: automatically updates every time the record changes

Two Guards: XSD and JSON Schema

When you upload data, the backend validates it twice — once against an XSD schema for XML files and once against a JSON Schema for JSON files. Like two security checkpoints — one for each language your data might speak.

X

XSD Validation

Checks XML structure: is the root element correct? Are required fields (name, slug) present and non-empty?

J

JSON Schema Validation

Checks JSON format: are types correct? Does the slug match the regex pattern ^[a-z0-9]+(?:-[a-z0-9]+)*$?

The Validation Code

CODE 
// backend/src/utils/validateXml.ts
function validateCategoryNode(el, errors) {
  const nameEls = el.getElementsByTagName("name");
  if (nameEls.length === 0) {
    errors.push("Missing 'name'");
  } else if (!nameEls[0]?.textContent?.trim()) {
    errors.push("'name' must not be empty");
  }
}
PLAIN ENGLISH

This function checks one category in the XML

Look for any <name> tags inside this category element

If there are zero name tags, that's an error — name is required

Add "Missing 'name'" to the list of problems

If the name exists but is empty or just spaces, that's also bad

Add a different error: name can't be blank

💡
Validate at the Boundary

Notice how validation happens at the entry point — where external data enters the system. This is a universal principle: trust nothing that comes from outside. Validate input once, at the border, then trust it internally. Like checking passports at the airport, not at every shop inside the terminal.

The Security Gate

How the app knows who you are, what you're allowed to do, and how it keeps your session alive — all without storing anything on the server.

JWT: Your Digital Wristband

Imagine a music festival. At the gate, you show your ticket and get a wristband. The wristband has your name and access level encoded into it. Every stage checks your wristband — but none of them need to call the box office. The wristband is the proof.

That's exactly how JWT works. The server creates a signed token with your identity inside. Every request sends this token, and the server verifies the signature — no database lookup needed.

CODE 
// backend/src/routes/auth.ts
const payload = { userId, email, role };
const accessToken = jwt.sign(
  payload,
  JWT_SECRET,
  { expiresIn: "15m" }
);
const refreshToken = jwt.sign(
  payload,
  JWT_REFRESH_SECRET,
  { expiresIn: "7d" }
);
PLAIN ENGLISH

After verifying your password, the server creates two tokens:

The "payload" — your identity data baked into the token

Access token: your short-lived wristband, good for 15 minutes

It's signed with a secret key only the server knows

15 minutes keeps it safe — if someone steals it, it expires fast

Refresh token: your "re-entry pass," good for 7 days

Signed with a different secret (extra security layer)

When the access token expires, use this to get a new one without logging in again

Two Tokens, Two Jobs

A

Access Token

Stored in memory (a JavaScript variable). Lives 15 minutes. Sent with every request as a "Bearer" header. If stolen, damage is limited to 15 min.

R

Refresh Token

Stored in localStorage. Lives 7 days. Only used to get a new access token. Never sent with regular requests — reduces exposure.

The Middleware Guard

CODE 
// backend/src/middleware/auth.ts
export function authenticate(req, res, next) {
  const authHeader = req.headers.authorization;
  if (!authHeader?.startsWith("Bearer "))
    return res.status(401).json({...});
  const token = authHeader.slice(7);
  const decoded = jwt.verify(token, JWT_SECRET);
  req.user = decoded;
  next();
}
PLAIN ENGLISH

This function runs before protected routes — like a bouncer

Grab the "Authorization" header from the request

If there's no header, or it doesn't start with "Bearer " — reject (401 Unauthorized)

Extract just the token part (skip the "Bearer " prefix, 7 characters)

Verify the signature using the server's secret key — this proves it's genuine

Attach the decoded user info (id, email, role) to the request object

Call next() — "this person checks out, let them through to the route"

💡
Middleware: The Assembly Line

Middleware is one of the most powerful patterns in web development. Each request passes through a chain of functions — authentication, permission checking, logging — before reaching the actual route handler. If any middleware says "stop," the chain breaks and the request is rejected.

Clever Patterns

The engineering tricks hidden in this codebase — patterns you can request from AI tools by name once you know they exist.

Patterns Worth Knowing

Think of these as power tools in your workshop. You don't need to build them from scratch — you just need to know they exist, what they're called, and when to reach for them. That's enough to tell an AI "add the proxy pattern here" and get exactly what you want.

P

Proxy Pattern

Backend translates between REST and gRPC. Browser says "give me weather" in REST; backend translates to gRPC and forwards to the specialist server.

T

Two-Token Auth

Short-lived access token (15min) + long-lived refresh token (7d). Balances security with convenience — like a day pass and a season ticket.

S

State Separation

Zustand for auth state (transient, in-memory). TanStack Query for server data (cached, auto-refreshing). localStorage for the refresh token (persistent).

A

API Source Toggle

A settings flag (USE_CUSTOM_API) switches between local Prisma DB and external Strapi. Same routes, different data source — the adapter pattern in action.

XPath: The XML Search Engine

The SOAP service uses XPath to search through XML — it's like SQL but for XML documents. Watch how a case-insensitive search is built:

CODE 
// backend/src/soap/categoriesService.ts
const xpathQuery = `//category[
  contains(
    translate(name, 'ABC...Z', 'abc...z'),
    '${term}'
  ) or contains(
    translate(description, 'ABC...Z', 'abc...z'),
    '${term}'
  )
]`;
const nodes = xpath.select(xpathQuery, doc);
PLAIN ENGLISH

This file handles SOAP search operations

Find all <category> elements anywhere in the document (//) where...

...the name, converted to lowercase (translate does letter-by-letter swapping)...

...contains the search term

OR the description, also lowercased, contains the term

(XPath has no toLower() function, so translate() is the workaround)

Run the XPath query against the parsed XML document and get matching nodes

Frontend: The Auto-Refresh Hook

CODE 
// frontend/src/store/authStore.ts
getToken: async () => {
  const { accessToken } = get();
  if (accessToken) {
    const decoded = decodeJwt(accessToken);
    if (decoded.exp * 1000 > Date.now() + 60000)
      return accessToken;
  }
  const rt = localStorage.getItem("refreshToken");
  const data = await refreshApi(rt);
  _setAuth(data.accessToken, ...);
  return data.accessToken;
}
PLAIN ENGLISH

This function is called before every API request

Grab the current access token from the Zustand store

If we have one...

Decode it and check the expiration timestamp

If it's valid for more than 60 seconds, it's still good — use it

(the 60-second buffer prevents using a token that's about to expire)

Otherwise, grab the refresh token from localStorage

Call the server's /auth/refresh endpoint to get a new access token

Update the Zustand store with the fresh token

Return it — the original API call never knew anything happened

When Things Break: Where to Look

Debugging is like being a detective. The trick is knowing which room to investigate based on the symptom. Here's your cheat sheet:

401 Unauthorized "Token expired or missing." Check: Is getToken() returning a valid token? Is the refresh token in localStorage? Look at authStore.ts and middleware/auth.ts.
403 Forbidden "Valid token, wrong role." Check: The user's role in the database. Look at middleware/auth.ts requireWriteAccess().
SOAP returns empty "XPath found nothing." Check: Does categories.xml exist? Was it generated? Is the search term matching? Look at soap/categoriesService.ts.
Weather timeout "gRPC server not running or DHMZ down." Check: Is port 50051 listening? Can you reach vrijeme.hr? Look at grpc-server/src/server.ts.
Upload validation fails "XML or JSON doesn't match schema." Check: Does XML have <name> AND <slug>? Does JSON slug match the regex? Look at routes/upload.ts and utils/validateXml.ts.
